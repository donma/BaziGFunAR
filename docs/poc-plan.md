## 桌面已驗證的事實

- `npm run build`：PWA manifest、autoUpdate SW、precache 18 項（約 2.27 MB）、模型 CacheFirst 規則（`bazigfunar-models-v1`）皆產出。
- `npm run smoke`（真 Edge，假相機）：
  - 首次引導建立人物→進入 AR，HUD 與快門正常渲染，零 console 錯誤。
  - 相機串流運行（`相機✓`），模型背景載入完成（`AI 就緒`）。
  - 快門一次產生 1 筆紀錄＋2 張照片（raw/ar）、schema 2。
  - Cache Storage 有 `bazigfunar-models-v1`；Service Worker 已接管頁面。
- 模型 URL 與 shard 解析已修正並以真實 HTTP 請求驗證（先前 shard 被錯拼在 `model.json/` 底下，已加回歸測試）。

## 結論與風險

1. **可達成**：本機相機＋方向感測管線、模型背景載入與離線快取、2D 追蹤與貼紙渲染、雙照片與匯出、命理一致性（107 測試）。
2. **需降級／明確標示**：
   - 門窗不是模型類別 → 一律「幾何候選・待確認」，需使用者確認（規格 6 允許）。
   - 無原生空間錨定 → 標籤分「朝向參考／住宅宮位已確認（選用，依使用者中心確認）／待確認」，不假裝 3D 定位。
3. **未達標（待實機才能判定）**：辨識率、追蹤漂移、30 FPS、10 分鐘穩定性、iOS/Android 授權與旋轉行為。**不得據本報告宣稱任何百分比或支援機型。**
4. 若實機證實 2D 吸附不穩定，依規格第 14 節改用懸浮式備援（見 `src/ar/spatial.ts` 的 pending 狀態），**不得**轉為原生 App 或付費雲端 AI。

## 實機 PoC 執行步驟（交接用）

1. 部署 `dist/` 到 HTTPS（GitHub Pages / Cloudflare Pages）。
2. iPhone Safari（加入主畫面 PWA 也測一次）與 Android Chrome 分別：
   - 允許／拒絕相機與方向感測，檢查停止畫面（決策 20A）與重新授權。
   - 在已知方位（北／東／南／西）記錄 HUD 角度、宮位、吉凶與原始 API 欄位。
   - 對門／窗／桌／床／沙發各拍 20 張以上，記錄正確、誤判、漏判；門窗需記錄「幾何候選」是否被正確確認。
   - 慢速轉向、輕微晃動、短暫遮擋，錄影並檢查貼紙跳動／淡出。
   - 連續 10 分鐘記錄 FPS、推論耗時、記憶體與相機是否中斷。
   - 離線（開啟過一次後關網路）檢查 AI 仍就緒；清快取後檢查誠實提示。
3. 將量測結果填入 `docs/acceptance.md` 的實機欄位，未測欄位保持「待實機」。
